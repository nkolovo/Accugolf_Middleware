## Real bugs found + fixed this session

- `net48` had **never actually compiled** before this session — multiple real API mismatches against the installed SDK (logging handler signature, `GetTLStreamNodeMap()` not `GetStreamNodeMap()`, `.ManagedData` not `.GetData()`), plus .NET Framework doesn't have `MathF`/`Math.Clamp` (added [Compat/NetFrameworkCompat.cs](../Compat/NetFrameworkCompat.cs) polyfill), plus a `record` type needing `IsExternalInit` (swapped for a tuple in [StereoCalibrator.cs](../Vision/Calibration/StereoCalibrator.cs)).
- **Camera left/right was backwards** — see camera roles above. Would have silently degraded all real detections to low-confidence monocular tracking.
- `StereoRectifier` was built at startup but **never actually applied to frames** — triangulation was running on unrectified coordinates. Fixed in [SimulatorEngine.cs](../App/SimulatorEngine.cs) (`RectifyFrame`), which is also a hard prerequisite for the 3D spin work (needs epipolar-rectified rows for stereo point matching).
- `fy = fx * (cy/cx)` in [StereoCalibrationData.cs](../Vision/Calibration/StereoCalibrationData.cs) was mathematically wrong for a square-pixel sensor (fy should just equal fx, independent of aspect ratio) — fixed, regression test added.
- `net48`'s `UdpClient` has no cancellable `ReceiveAsync(CancellationToken)` — [UdpTransport.cs](../Transport/UdpTransport.cs) now uses the standard close-the-socket cancellation pattern (works on both targets).
- `FindStereoMatch`'s original fixed 60px disparity search window was far too small for this rig's real geometry (~289px expected disparity at the ball spot, ranging ~170–870px across a shot's depth). Now searches around an *expected* disparity derived from the ball's own just-triangulated position each frame.
- Normalized correlation is degenerate (spurious high-confidence match) on a textureless patch — added a variance guard in [FeaturePointTracker.cs](../Vision/FeaturePointTracker.cs).

## Spin measurement — two tiers, know the difference

**Why two systems exist:** a single camera watching from nearly overhead can only see rotation about its own viewing axis. Backspin/topspin and a tumbling field-goal kick both rotate about a *horizontal* axis lying in the image plane — invisible to simple 2D correlation from this rig's mounting angle. Sidespin/curl (vertical axis) is the one case simple 2D correlation handles well here.

1. **[SpinEstimator.cs](../Vision/SpinEstimator.cs)** — single-camera 2D rotation correlation. Magnitude only, no axis. Reliable only where spin rate stays under ~90°/frame at 200fps (soccer's ~300–600rpm; NOT golf/baseball/tennis, which alias badly — and golf/tennis are out of scope anyway).
2. **[RotationFitter.cs](../Tracking/RotationFitter.cs) + [FeaturePointTracker.cs](../Vision/FeaturePointTracker.cs) + [Spin3DEstimator.cs](../Vision/Spin3DEstimator.cs)** — full 3D spin (magnitude AND axis), built this session. Natural-texture tracking (GFTT corners + optical flow + rectified stereo matching + Kabsch rigid-rotation fit), not marked/painted balls — chosen to avoid a practice-ball workflow change. Wired into `SimulatorEngine`; populates `BallData.SpinAxisX/Y/Z` for the first time. Takes priority over the 2D estimate when it produces a valid fit.

**Both are covered by unit tests against synthetic data (149 tests total, all passing) — this proves the math and wiring are correct. It does NOT prove real ball surfaces have enough natural texture contrast at 720×540 under real lighting for GFTT to track reliably. That's the biggest open unknown, only checkable against real footage.**

Ball choice matters: cameras are monochrome, so only grayscale contrast counts, not color. A classic black/white pentagon ball is the safer bet — a modern colorful ball can look flat/featureless in grayscale even if it looks richly patterned to the eye.

**Live validation added:** `SimulatorEngine` now prints `[Spin3D] rpm=... axis=(x,y,z) points=N` every time the 3D fit succeeds (unthrottled — whether this line appears at all is itself diagnostic), and a throttled `[Ball] pos=... speed=... tier=... spin=...` trajectory line (~10Hz) during tracking. To sanity-check axis output against real shots: a pure backspin shot should show `axis.X` dominant; a pure sidespin/curl shot should show `axis.Z` dominant with a smaller `axis.Y` (~±0.28, from the known 16.15° tilt) — not noise, expected geometry. `AxisUnit` is camera-relative, not yet rotated into labeled backspin/sidespin/spiral terms.

## Sport-specific spin decisions

- **Soccer**: real spin wanted and achievable (2D or 3D).

- **Tennis**: dropped from scope entirely (that game won't be made).

## 2026-07-22 follow-up — four real bugs found running the mock pipeline live (not just unit tests)

Nikolas asked to smoke-test the Unity integration with `MockCameraManager` before kicking a real ball. Doing that live (`dotnet run -f net10.0-windows`) surfaced **four bugs that the 149 unit tests never caught**, because unit tests exercise each class in isolation with hand-crafted inputs — none of them ran the full camera→detect→rectify→triangulate→send pipeline together, live, with realistic timing. All four affect **real hardware operation identically**, not just the mock — this wasn't mock-only cleanup.

1. **`StereoRectifier.Build()` never actually called `CvInvoke.StereoRectify`.** It read `cal.R0/P0/R1/P1` directly and fed them to `InitUndistortRectifyMap` — but those fields are rectification *outputs* (see class comment on `StereoCalibrationData`), populated only by `StereoCalibrator.Calibrate()` for a real checkerboard run. Via `CreateDefaults()`'s fallback (no calibration file yet — see item 1 above), they were still zero, so `Triangulator.Configure` read `fx=0`/`baseline=NaN` and every 3D position came out `NaN`. Fixed: `Build()` now calls `CvInvoke.StereoRectify(K0,D0,K1,D1,imgSize,R,T,...)` itself and writes the real R0/R1/P0/P1/Q back into `cal`, mirroring what `StereoCalibrator` already did for the real-calibration path. [StereoRectifier.cs](../Vision/Calibration/StereoRectifier.cs)
2. **`MockCameraManager` drew a fixed 6px-radius blob (~113px² area) regardless of sport** — soccer's `MinContourArea` is 800px², so the mock ball could never pass `BallDetector`'s contour filter. Fixed: blob radius is now sized from the active profile's contour-area midpoint. [MockCameraManager.cs](../Vision/MockCameraManager.cs)
3. **The real one, hardest to find: `SimulatorEngine.RectifyFrame`'s Mat→byte[] readback used a per-pixel `Matrix<byte>` indexer loop (388,800 individual calls) over the full 720×540 frame** — ~14ms measured per frame, slower than the ~5ms/frame budget at 200fps. The (bounded, 256-cap) frame queue backed up faster than it could drain, so an entire 2-second mock shot collapsed into one giant stale batch by the time processing caught up — `det0`/`det1` only ever reflected the *last* frame in that backlog (usually off-screen by then), so **zero or one `BallData` packet got sent per shot** instead of a live stream. `BallDetector.ExtractCrop` uses the same indexer-loop pattern safely because it only ever operates on a tiny 48×48 crop — the bug was applying that pattern to a full frame. Fixed with a direct bulk `Mat.CopyTo(byte[])` (same approach `MatToArray` already used for calibration doubles). This dropped per-frame cost from ~14ms to ~1-2ms and let real-time throughput through. Found this by adding (and then removing) stopwatch instrumentation around each pipeline stage live — worth remembering as a debugging approach if throughput problems show up again with real hardware. [SimulatorEngine.cs](../App/SimulatorEngine.cs)
4. **`StereoCalibrationData.CreateDefaults()`'s `T` (stereo translation vector) had the wrong sign.** OpenCV's convention is `X_cam1 = R·X_cam0 + T`; for camera1 (right) sitting physically further +X than camera0 (left), `T`'s X component must be *negative* — `CreateDefaults` had it positive, which (combined with `Triangulator`'s correct, standard `baseline = -P1[0,3]/P1[0,0]` formula) made every computed baseline come out negative, which made every real-stereo Z land outside the sane `[0.05m, 10m]` range, which silently self-demoted `TriangulateStereo` to its internal `Monocular()` fallback — which hardcodes `X=Y=Z=0`. So even *after* fixing bug #1 and #3, every ball position reported was exactly `(0,0,0)`. Fixed by negating `T` in `CreateDefaults`; updated the two `StereoCalibrationDataTests` that had asserted the (wrong) positive sign as their contract. [StereoCalibrationData.cs](../Vision/Calibration/StereoCalibrationData.cs)

**After all four fixes**, a live mock run produces genuinely correct output: `[Triangulator] Baseline: 495.3mm  fx: 1757.7px` (was `NaNmm  0.0px`), and `[Ball]` lines show a real, physically sensible trajectory (Z increasing as the ball flies away, Y rising then falling under gravity, `tier=FullStereo` with conf≈0.94 during the stereo-agreement window). All 149 tests still pass.

**Not yet re-validated against Unity itself** — this confirmed the middleware's own pipeline now produces real `BallData`, but the actual UDP send → `UdpReceiverNew` → `BallController` hop (see item 4 in "Still open" above) hasn't been re-tested live since these fixes landed.

## 2026-07-22 second follow-up — reported ball speed was ~10x too low, two more real bugs

Nikolas ran the fixed mock pipeline end-to-end into Unity: the ball moved, but never reached the net. Root-caused to two further bugs (found by adding, then removing, live instrumentation — Console.WriteLine per frame is itself slow enough to distort the timing being measured, a real observer-effect trap; cheap in-memory counters printed only on the existing throttled log line were the reliable way to see what was actually happening without changing it).

1. **`KalmanBallTracker` hardcoded `dt = 1/199.76f` into its transition matrix**, assuming every `Update()`/`Predict()` call corresponds to exactly one camera tick. It doesn't — `SimulatorEngine.ProcessLoop` batches a variable number of frames per cycle (observed `drain=2` up to `drain=20` depending on processing load at that instant), so the real elapsed time between tracker calls routinely exceeded the assumed ~5ms by a wide margin. That silently and systematically underestimated recovered velocity. Fixed: `Update`/`Predict` now take the frame's actual `TimestampUs`, and the transition matrix's dt is rebuilt each call from the real elapsed time since the previous one (clamped `[1e-4s, 0.5s]` against duplicate timestamps / long coasts). Updated `KalmanTrackerTests.cs`/`KalmanTrackerAdditionalTests.cs` to pass explicit timestamps matching their own `dt` variables. [KalmanBallTracker.cs](../Tracking/KalmanBallTracker.cs)
2. **The real remaining blocker: `MockCameraManager` silently modeled a completely different camera than the one `StereoCalibrationData.CreateDefaults()` (and therefore `StereoRectifier`/`Triangulator`) assumes.** Mock generated 1280×1024 frames at fx=1800 (stale numbers, predating the on-site confirmation of the real camera's specs); `CreateDefaults()` builds a 720×540/fx≈1757.7 model. Nothing throws on this mismatch — it just makes `StereoRectifier`'s remap tables sample from the wrong place, which **washed out real disparity almost entirely**: true disparity at working distance should be ~290px, but detected (post-rectify) disparity measured only ~4-5px. That's why `TriangulateStereo` self-rejected on every single attempt (disparity too small even to clear the `disparity <= 0.5f` "behind baseline" guard, some of the time) — not a range or sign issue this time, the two cameras' images had been rectified into near-agreement with each other, destroying the very depth cue triangulation needs. Fixed by exposing the real camera model's constants as `public const`/`static` members on `StereoCalibrationData` (`DefaultImageWidth/Height`, `DefaultFx`) and having `MockCameraManager` reference them directly instead of maintaining an independent, silently-driftable copy. Also updated `MockCameraManagerTests.cs`'s hardcoded `1280×1024` assertions to reference the same constants. [MockCameraManager.cs](../Vision/MockCameraManager.cs), [StereoCalibrationData.cs](../Vision/Calibration/StereoCalibrationData.cs)

Also, while chasing this, found the mock's default ball-start position (0.5m from camera) and default trajectory (30 m/s / 15°, a full-power drive-distance kick) put most of a shot's flight either deep inside `Triangulator`'s close-range zone or past its 10m far-range cutoff — nowhere near the real rig's confirmed ~3m working distance. `Program.cs`'s mock setup now starts the ball at ~3m (`MockCameraManager.BallStartZ`) and uses a more modest 12 m/s / 8° trajectory representative of a shot actually captured near the tee, with Unity's own local physics (`BallController`) carrying the rest of the flight — matching the intended "brief burst capture near the tee, not a full continuous track" design in [11-unity-integration.md](11-unity-integration.md).

**After both fixes**, a live run shows sustained `tier=FullStereo` (not a 2-cycle fluke), confidence 0.92–0.94, and speed climbing correctly toward the true trajectory value across successive real measurements (observed 3.2→5.1→6.1→6.5→7.0 m/s converging toward the 12 m/s truth) — genuine Kalman convergence from its zero-velocity prior, not a stuck/wrong steady-state. **Still open**: full convergence to the exact true speed takes more real measurements than a very short capture window provides (the existing `KalmanTrackerTests.cs` comment already notes "typically 200-400 frames to reach steady state" for this filter/tuning) — worth watching whether reported speed is close enough for a satisfying Unity shot, or whether the filter needs faster-converging tuning (e.g. seeding initial velocity from the first two measurements instead of zero) if it's consistently undershooting in practice. All 149 tests pass throughout.

## 2026-07-22 third follow-up — velocity seeding, spin noise, and a mid-shot reset bug

At 18 m/s the previous fix's two-point velocity seed proved noise-sensitive: dividing a small noisy displacement (stereo depth noise ≈6cm at Z=5m, per `Triangulator.DepthPrecisionMm`) by a small dt (~5ms, ~9cm of true displacement at 18 m/s) amplifies detection noise into a wildly inaccurate velocity — worse the shorter the gap between the two seed points. Replaced with a least-squares line fit (position vs. time, independently per axis) through the first 8 real measurements (`KalmanBallTracker.SeedFromBuffer`) — averages out independent per-measurement noise roughly by `√N` instead of amplifying it. `KalmanTrackerTests.cs` updated (some tests only fed 2 measurements, matching the old design).

Separately, Nikolas reported the ball orbiting in a circle before reaching the net — traced to `[Spin3D]` readings swinging wildly frame to frame (single digits to 5000+ rpm). Root cause: `MockCameraManager`'s ball was a perfectly flat white disc with zero internal texture, so `FeaturePointTracker`'s GFTT corner detector was tracking edge/threshold noise, not real features — and `BallController` applies that spin directly as a Magnus force, so one bad ~5000rpm reading with a near-vertical axis was enough to send the ball into a sustained curve. Added fixed internal speckles to the mock ball (`MockCameraManager._speckleOffsets`, never rotated — matching the physical truth that this mock doesn't model spin at all) so the tracker has real points to find; this alone wasn't sufficient (still saw occasional 5000+ rpm — visually-identical speckles are genuinely ambiguous for `FindStereoMatch`'s cross-camera template matching, unlike a real ball's locally-distinctive seams/panels). Added a direct plausibility guard in `Spin3DEstimator.Estimate`: reject any reading above 1500rpm (well beyond any in-scope sport's real range — golf's much higher real spin is out of scope) rather than feed a physically-impossible value into the Magnus force. This is what actually stops the orbiting; the speckle texture is a secondary improvement, not a full fix — true spin accuracy validation still needs a real textured ball on real hardware.

Then: "why is it sending multiple shots?" — it wasn't. `[Ball] speed=15.2m/s` two lines later becomes `speed=0.0m/s` — the tracker's converged velocity got wiped mid-flight. Cause: Unity's `ProfileSelectSender` resends `"soccer"` up to 5 times over ~8s after Play (no ack in this protocol, so it can't know if the first one landed — see notes above on retry behavior). Every resend, even for an already-active profile, went through `SimulatorEngine.OnProfileCommand` → `ApplyProfile` → `KalmanBallTracker.Configure()`, which builds a **brand new** `KalmanFilter` from scratch. Since the mock's 2-second shot fires within that same retry window, a redundant resend landing mid-flight silently reset tracking to zero. This is a real bug for any deployment, not mock-specific — I'd flagged the theoretical risk earlier in this session but hadn't yet seen it actually bite. Fixed: `OnProfileCommand` now short-circuits (`return`, no reset) if the requested `SportId` already matches `_activeProfile.SportId` — switching profiles still resets state when the sport actually changes, but redundant re-selection of the same sport is now a true no-op. All 149 tests pass throughout.

## 2026-07-22 fourth follow-up — root-caused the remaining velocity instability, verified against real camera specs

Nikolas correctly pushed back on an assumption: I'd been treating `MockCameraManager`'s injected `_positionNoisePx = 1.5f` detection noise as roughly realistic. He supplied the actual Blackfly S BFS-PGE-04S2M-CS spec sheet (720×540, 6.9μm pixel pitch, Sony IMX287 global shutter) — resolution matched what `StereoCalibrationData.CreateDefaults()` already models, confirming that part was solid. But the noise figure wasn't really about camera optics at all — it was about how precisely `BallDetector` locates the ball within that pixel grid, which is a software question. Checked `BallDetector.Detect()` and found it was computing the center from `CvInvoke.BoundingRectangle` — `rect.X + rect.Width/2f`, both integers, so the reported center can only ever land on half-pixel increments. That's real, avoidable imprecision, not a hardware limit. Replaced it with an image-moment centroid (`CvInvoke.Moments` → `M10/M00, M01/M00`), the standard technique for genuine sub-pixel accuracy (~0.1–0.3px on a clean, well-contrasted blob this size) — benefits real hardware too, not just the mock. Reduced `MockCameraManager._positionNoisePx` from 1.5px to 0.3px to match what this improved detector can actually achieve, instead of modeling noise sized for the coarse method it no longer uses. [BallDetector.cs](../Vision/BallDetector.cs), [MockCameraManager.cs](../Vision/MockCameraManager.cs)

Spin got noticeably calmer after this (no more 1000+rpm swings), but reported speed was still unstable — worse, it now swung in *both* directions run to run (one run seeded at 33.8m/s against an 18m/s truth, another at 2.8-6m/s), and once seeded, the filter wasn't correcting back toward the truth even after many subsequent real measurements. Added a one-shot diagnostic print inside `KalmanBallTracker.SeedFromBuffer` and found the real cause: **every single one of the 8 buffered seed measurements was exactly `(0.000, 0.000, 0.000)`.** This was the same self-referential bootstrapping bug already fixed for Tier 3 (see the third follow-up above — `TriangulateMonocular` needs an existing Z reference, and before any real fix, that reference is a meaningless 0) — but present in a *different*, ungated code path: when `TriangulateStereo` itself self-rejects internally (returns its hardcoded `(0,0,0)` Monocular fallback), `SimulatorEngine`'s "enrich with the Kalman's last Z" logic was *also* using `_tracker.LastState.z`, which is equally meaningless before `HasFix` is true. The `HasFix` guard I'd added earlier only covered the Tier 3 branch, not this Tier 1-self-reject-then-enrich branch. Fixed by applying the same `HasFix` check there: before a real fix exists, a self-rejected stereo attempt now coasts (`TriangulationTier.KalmanOnly`, routed to `Predict()` not `Update()`) instead of feeding a fabricated zero into the seed buffer.

**After this fix**, four consecutive live runs at the 18 m/s test trajectory all converged to **19-20 m/s** — no more run-to-run variance between 2.8 and 33.8, no more decay after seeding, stable through the whole tracked flight. This was very likely the dominant remaining cause of "the ball changes direction/speed unpredictably" — the earlier fixes (dt, least-squares seeding, sub-pixel centroid, spin cap) were all real and necessary, but this bootstrapping bug was corrupting the seed's actual input data regardless of how good the fitting math on top of it was. All 149 tests pass throughout.

Position/velocity was now solid, but Nikolas reported the ball still "doing squiggly lines but going straight" in Unity — net displacement roughly correct, path visibly jittery along the way. Confirmed via log: even with the 700rpm plausibility cap holding (see third follow-up), the recovered spin **axis** kept flipping direction almost every reading (`(-0.87,0.46,0.14) → (-0.06,1.00,-0.01) → (-0.97,0.19,0.15) → (0.56,-0.80,0.21) → ...`), and `BallController.ApplyHit` overwrites the ball's Magnus-force spin vector on *every* packet received — far more packets per second than the throttled `[Ball]` log shows. A rapidly, randomly rotating axis reads as exactly this: a jittery/squiggly path whose random perturbations average out to roughly straight net motion, rather than a single clean curve. This is the same underlying issue as the orbiting bug two follow-ups back, just less severe post-cap — magnitude limits can't fix an axis that has no real signal in it, because the mock's ball has no real rotating texture for either spin estimator to measure.

Concluded that chasing tighter thresholds on Spin3D's output was a dead end for mock testing specifically, and disabled spin estimation entirely when `SimulatorEngine` is constructed with a `MockCameraManager` (`_skipSpinEstimation`, checked in `ProcessLoop` before calling `UpdateSpinEstimate`/`UpdateSpin3D`) — `SpinRpm`/`SpinAxis*` now report a clean `0` for the whole mock-tested flight, verified live (no `[Spin3D]` lines at all, `spin=0rpm axis=(0.00,0.00,0.00)` on every sample). Real spin validation still needs a real textured ball on real hardware — this flag only affects the mock path; `CameraManager` (real Spinnaker cameras) is unaffected and will still run both spin estimators normally. All 149 tests pass.

## 2026-07-22 fifth follow-up — a genuinely off-center shot exposed two more real bugs (per-camera background, ghost-trail contour growth)

With straight (azimuth=0) shots solid, Nikolas asked for a shot aimed left-of-center — the first time this session a shot had real, sustained lateral motion instead of mostly-depth motion. Nothing about position/spin worked at all: zero `[Ball]` output regardless of azimuth magnitude (-15°, -8°). This surfaced two more real bugs that a straight-down-the-middle shot happens not to trigger.

1. **`BallDetector` used a single shared background Mat for both cameras.** With `SimulatorEngine` running one `BallDetector` instance for the whole stereo pair, camera 0 and camera 1's frames were diffed against a background that was really an alternating blend of both distinct viewpoints. For a dead-centered shot (both cameras seeing a similar-looking, similarly-positioned view) this blend happened to be harmless by coincidence. With real lateral motion the two views diverge enough that the shared/blended background produces spurious near-identical "detections" in both cameras — confirmed by instrumenting `Triangulator.TriangulateStereo`: a "detected" disparity of ~3px implied a nonsensical depth of 254 meters, nowhere near the ball's real ~3m starting distance. Fixed: `BallDetector` now keeps a `Dictionary<int, Mat>` of backgrounds keyed by `CameraIndex`, so each camera's frames are only ever diffed against its own history. [BallDetector.cs](../Vision/BallDetector.cs)
2. **The rolling background's decay rate (0.95 old / 0.05 new per frame) left a growing "ghost trail."** After fixing bug #1, detection worked briefly then died permanently a few frames later. Instrumented contour area directly and watched it climb steadily frame over frame — 5512 → 7868 → 13730 → ... → 10562px² — until it exceeded soccer's 8000px² ceiling and got rejected for good. The exponential-average background takes ~20 frames to "forget" a pixel the ball recently occupied; for depth-only motion that stale trail stays small and localized (why straight shots worked fine), but a ball sweeping laterally across the sensor leaves a trail spanning many distinct pixel positions, which morphological Close merges into one ever-growing contour with the ball itself. Fixed by making the decay faster (0.7/0.3) so the background catches up within a few frames regardless of travel direction. This is a real, general detection-quality issue — any real ball crossing the frame rather than flying straight back would hit the same growth — not a mock-only patch.

**After both fixes**, two consecutive live runs of a -8° azimuth shot tracked continuously start to finish: X sweeping steadily from 0 to about -2m (left, as intended), Z advancing normally, speed decaying smoothly from ~16 to ~14 m/s, spin holding at a clean 0 throughout (per the fourth follow-up's fix). All 149 tests pass.

Also (separately): re-tested the "azimuth off-sensor limit" claimed earlier in this follow-up. It was wrong — made before the two bugs above were found, so it was actually those bugs failing, not a real FOV exit. Retested empirically with them fixed: -15° now tracks cleanly (7 samples), -18° barely works (3 samples, right at the edge), -20°/-25° genuinely fail (off-sensor). Corrected `Program.cs`'s comment and settled on `azimuthDeg: -15f` as a shot with good margin. Also verified (and explained) why `azimuthDeg: 45f` fails: `azimuth` and `launchAngle` are independent parameters in this trajectory model, not components of one combined aim direction — 45° azimuth means 45° of *pure horizontal* deflection (far more extreme than the ~15-18° real limit), not a corner-seeking diagonal shot. The geometric intuition that a rectangular FOV's corner is farther from center than either edge alone is correct, but doesn't apply here since the two angles don't compose that way in this API, and the existing 8° launch angle already sits close to this rig's tighter vertical FOV limit (~8.7°), leaving little vertical headroom regardless.

## 2026-07-22 sixth follow-up — one consolidated shot result per ball, not a continuous stream

Nikolas asked why the middleware was sending 140+ individual `BallData` packets per shot (the throttled `[Ball]` console log only shows every 20th send) rather than one final result, as `notes/11-unity-integration.md`'s original design explicitly called for ("Emit one message to Unity... Unity doesn't need raw frames — it needs the shot result") and as his own earlier `SimulatedHitSender` mock already did. Continuous per-cycle sending was never a deliberate design choice — it's just what `SimulatorEngine.ProcessLoop` had always done, and this session's fixes were all about making that stream *accurate* without anyone stepping back to check whether streaming was the right model at all.

Changed `SimulatorEngine` to cache the latest real (non-`KalmanOnly`) measurement into `_pendingShotData` every cycle instead of sending it immediately, and only actually call `_udp.Send(...)` once — in the Tier 4 coast-timeout branch, exactly when `_coastFrames` exceeds the limit and the ball is judged genuinely gone (`SendPendingShotAndReset`). That single send uses the Kalman filter's fully-converged state as of the last real detection — i.e. its fused best estimate incorporating every measurement across the whole visible flight, which is exactly "one modeled, accurate trajectory taking multiple frames into account," not a separate aggregation step needed. After sending, resets the tracker (`_tracker.Configure`), coast counter, and spin state so the next shot starts clean. Renamed the throttled per-cycle console log from `[Ball]` to `[Tracking]` (diagnostic-only now, no longer indicates a send) and added a distinct `[Shot] Sent final result: ...` line for the actual send event.

Caught one bug in this myself before shipping it: caching on `pt3d.Tier != KalmanOnly` alone wasn't sufficient — the Kalman tracker reports a placeholder zero velocity while still gathering its 8-sample seed buffer (see `KalmanBallTracker.Update`), and those early cycles ARE tagged with a "real" tier (e.g. `FullStereo`) even though `HasFix` is still false. A brief early coast blip during that gathering window sent a spurious `speed=0.0m/s` "shot" before real tracking had even begun. Fixed by additionally gating the cache on `_tracker.HasFix`.

**Verified live**: two consecutive runs each produced exactly one `[Shot]` line, sent at the natural end of tracking. One converged close to the true 18 m/s trajectory (15.3 m/s final); the other undershot (4.2 m/s, following a sharp drop right at a FullStereo→Monocular tier transition) — this is the same underlying Kalman/tracking-quality variance this whole session has been chasing, now visible as a single number instead of buried in a 140-packet stream, not a new bug from this change. All 149 tests pass (no existing test exercised `SimulatorEngine`'s send behavior directly, so nothing needed updating).

## 2026-07-22 seventh follow-up — Tier 3 monocular drift: fixed properly, no cap needed after all

The sixth follow-up's single-shot design surfaced a real bug in `Triangulator.TriangulateMonocular`: when only one camera detects the ball, its X/Y/Z all derive from a single pixel position plus the Kalman tracker's own last-known Z — not an independent measurement. Feeding that straight into `_tracker.Update()` is circular: the filter "confirms" a value it produced itself, so any small Z-velocity error compounds unboundedly the longer a monocular streak runs. Found live at 25 m/s (faster shots spend longer per real-time interval in this state): the final result diverged to a nonsensical `pos=(10.61,6.61,55.41)`.

First attempt capped how many *consecutive* monocular fixes could feed `Update()` before falling back to coasting (`MaxConsecutiveMonocular`, tried 5 then 15) — both values appeared to cap out almost immediately (frozen final result around Z=9.35m every time, barely past the first couple of real stereo ticks), which looked like the cap was still far too low. That diagnosis was itself wrong, chased down a red herring: those particular test runs were executing a *stale* binary. `dotnet run --no-build` resolves to `bin/Release/net10.0-windows/`, while `dotnet build` for this project (with an implicit x64 platform) writes to `bin/x64/Release/net10.0-windows/` — the two silently diverge, and `--no-build` doesn't fail loud when the binary it finds is old. Running the actual freshly-built exe directly (`./bin/x64/Release/net10.0-windows/SportSimulator.exe`) tells the real story: a queue-backlog check confirmed the process loop keeps up fine with the mock's 200fps generation rate (backlog stayed at 0-2 frames), so throughput was never the issue either.

The real fix needed no threshold at all: route Monocular-tier results through `_tracker.Predict()` instead of `_tracker.Update()` — exactly like a genuine coast tick — so a non-independent measurement can never feed back into the filter's own belief. `MaxConsecutiveMonocular`/`_consecutiveMonocularTicks` were removed entirely as dead weight once this landed. **Verified live** (correct binary): an 18 m/s shot now tracks cleanly through 2 `FullStereo` ticks then dozens of stable `Monocular` ticks (speed locked at 16.7 m/s, no drift) all the way to `[Shot] Sent final result: pos=(3.74,2.65,16.64) speed=16.7m/s`, instead of freezing at ~9.35m. Re-testing the previously-broken 25 m/s case: speed stays locked at 22.9 m/s the whole flight (previously it read a corrupted 4.4 m/s mid-shot) and the trajectory's X/Y/Z ratios stay consistent with the launch/azimuth angles throughout — no divergence. All 149 tests pass.

Also answers a question Nikolas raised about whether launch angle (height) causes frame-exit the same way azimuth does: it doesn't, and the "11.6 degrees" framing from earlier in this doc was already flagged as wrong once the shared-background/ghost-trail bugs were fixed — restated more precisely in `App/Program.cs`'s trajectory comment. The sensor's rejection check (`MockCameraManager.ProjectToCamera`) is a rectangular pixel-bounds test, not a single radial half-angle from center — azimuth (X) and launch angle (Y) push the ball toward different edges of that rectangle, so being close to one axis's limit doesn't consume the other axis's budget. The current 15° azimuth + 14° launch angle shot never exits either camera's frame at all in this session's testing; the ball simply flies far enough in Z to leave *useful stereo range*, which is what ends tracking.
